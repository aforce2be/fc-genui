# FC 대상 Generative UI 개인 프로젝트 — 방향 정리

> 작성일: 2026-11-23 · 상태: 초기 기획 (가설 단계)
> 목적: 개발 실습 + 기획 포트폴리오 + **향후 회사 제안 가능성**. Claude Code로 구현.

---

## 1. 핵심 결정 사항

### 1-1. Gen UI 방식: ② 조합형으로 시작
| 수준 | LLM의 역할 | 검증 난이도 |
|---|---|---|
| ① 선택형 | 미리 만든 컴포넌트 중 선택 + 데이터 채움 | 낮음 |
| **② 조합형 (채택)** | 정해진 컴포넌트 카탈로그 안에서 JSON 스키마로 레이아웃 구성 | 중간 (자동화 가능) |
| ③ 생성형 | HTML/JSX 코드 직접 작성 | 높음 |

- 채택 이유: 출력 범위가 통제되어 검증 가능. 컴포넌트 카탈로그·디자인 시스템 설계는 퍼블리싱 경력과 직결.
- 원칙: **AI는 "무엇을, 어떤 순서로" 보여줄지 결정하고, "어떻게 생겼는지"는 디자인 시스템이 결정한다.**

### 1-2. 진입 화면: "UI 먼저, 입력창은 보조" 혼합형
| 영역 | 고정/생성 | 내용 |
|---|---|---|
| 뼈대 (헤더·내비·영역 배치) | 고정 | 항상 같은 위치 (공간 기억 유지) |
| 오늘의 브리핑 슬롯 | AI 조합 | FC 상황에 맞춰 카드 구성·우선순위 결정 |
| 의도 입력창 | 보조 | 자연어 요청 시 해당 슬롯만 재조합 |
| 대화 이력 | 숨김/선택 | 필요할 때만 펼침 |

- 대화창 우선을 택하지 않은 이유: 빈 입력창 진입 장벽, FC 업무는 반복적이라 "물어보기 전에 보여야" 함, 현장·모바일 사용으로 타이핑 최소화 필요.
- 전체 화면 자유 생성을 택하지 않은 이유: 레이아웃이 매번 바뀌면 업무 도구로서 치명적, 검증 난이도 최대.

### 1-3. 검증 체계 (단계별)
1. **스키마 검증** — Zod 등으로 카탈로그 규칙 준수 확인 (자동, json-render에 내장)
2. **렌더 검증** — Playwright로 렌더 에러 확인 (자동, pc/mo 뷰포트 각각)
3. **접근성 검증** — axe-core (자동)
4. **의도 적합성** — 스크린샷 + 요청을 LLM 판정자에게 주고 루브릭 채점 (반자동)
5. **사람 평가** — 고정 프롬프트 20~30개 골든셋으로 버전 간 비교

> 포트폴리오 관점: 결과물을 "Gen UI 데모"가 아니라 **"Gen UI 품질 기준과 평가 체계"**로 정의한다. "좋은 생성 UI란 무엇인가"를 정의하는 것이 기획의 몫.

### 1-4. 기술 스택: Nuxt 4 + Vue 3 (채택)
| 레이어 | 선택 | 비고 |
|---|---|---|
| 프레임워크 | Nuxt 4 + Vue 3 | 회사 Vue 생태계와 연결 |
| Gen UI | json-render (`@json-render/core` + `@json-render/vue`) | Vercel 오픈소스(Apache 2.0). Zod 카탈로그로 AI 출력 제한 |
| AI 연동 | AI SDK (`@ai-sdk/vue`) | 모델 교체 가능 (특정 LLM에 종속되지 않음) |
| UI | Nuxt UI 또는 자체 컴포넌트 카탈로그 | 카탈로그는 직접 설계 (회사 디자인 시스템 반입 금지) |
| 검증 | Zod, Playwright, axe-core | 1-3 검증 체계 |

- **채택 이유: 회사 제안 가능성.** 회사는 Nuxt 2 / Vue 2 사용 중. "Vue 생태계에서 이렇게 할 수 있다"가 React 데모보다 설득력이 높음.
- 부수 효과: Vue 2(2023년 말)·Nuxt 2(2024년 중반) 공식 지원 종료 상태이고, json-render Vue 렌더러는 Vue 3 전용 → **"Vue 3 전환 시 열리는 AI 기능"의 실제 사례**가 됨.
- 대안(Next.js + React)은 예제·생태계가 더 풍부하나 회사와의 연결성이 약해 제외.

### 1-5. 디바이스 전략: 하나의 명세, pc/mo 두 렌더링
- 확인된 사실: FC는 **아침에 지점으로 출근**하며, 회사에 **FC용 모바일 지원 앱이 이미 있음**.
- 결정: AI가 생성하는 JSON 명세는 디바이스와 무관하게 하나로 유지하고, **렌더링 규칙만 pc/mo로 분리**한다.

  | | pc (지점, 오전) | mo (현장, 오후) |
  |---|---|---|
  | 주 용도 | 아침 브리핑, 상담 준비 | 이동 중 고객 요약 확인 |
  | 카드 수 상한 | 5장 | 3장 (나머지는 "더보기") |
  | 레이아웃 | 2열 그리드 + 상세 패널 | 1열 스택 |
  | 입력 | 입력창 노출 | 입력창 최소화, 탭 중심 |

- 기존 모바일 앱과 중복 개발하지 않는다. 제안 시 **기존 앱에 웹뷰로 붙는 모듈**로 포지셔닝 (Nuxt 앱을 웹뷰로 탑재 가능한 구조).
- 카드 수 상한 같은 디바이스별 제약은 **카탈로그 규칙 + 스키마 검증으로 강제**.

## 2. 보험 도메인 제약

- **상품 추천 UI 지양** — 금융소비자보호법상 적합성·설명의무 이슈. AI는 FC 판단을 돕는 정보 정리(보장 공백, 갱신 일정 등)에 집중.
- **데이터 정책** — 실제 고객·회사 데이터 사용 금지. 가상의 FC·고객 목업 데이터로만 구현.
- **근거 표시** — AI가 카드를 상단에 올린 이유를 함께 노출 (예: "갱신일 3일 전"). 신뢰도와 검증 가능성 동시 확보.

## 3. FC 반복 업무 가설 (검증 필요)

> ⚠️ 한국 FC의 업무별 빈도·시간을 집계한 공개 통계는 찾지 못함. 해외 설계사 시간 배분 조사와 국내 업계 자료를 대리 지표로 사용. **FC 인터뷰로 반드시 검증할 것.**

### 근거 요약
- 미국 설계사 다수가 업무 시간의 25~50%를 영업에, 25~50%를 기존 계약 서비스·문제 처리에 사용하며, 행정·서비스 비중이 기대보다 높다고 인식 (ReSourcePro / Insurance Journal)
- 행정 업무가 생산 시간의 약 3분의 2를 차지한다는 분석 (Accenture, Datagrid 인용)
- 대리점 주간 업무 중 "고객과의 소통"이 29%로 가장 많으나 다른 업무와 근소한 차이 (Vertafore)
- 국내 설계사의 AI 활용 증가는 주로 상담 준비·설명자료 작성 영역. 신규 고객 발굴·최종 협상은 AI가 대체하기 어려움 (아시아경제, 업계 관계자)
- 삼성생명 컨설턴트 설문: 고객 선호 상품 건강보험 39.1% > 실손 22.1% > 연금 18.8% > 종신 12.5%. 5년간 가입 건수·사고보험금 지급 모두 건강보험 1위 (이코노미스트)
- 고지의무 정리, 미청구 보험금 산출, 청구서 작성이 반복 업무로 언급됨 (광고성 블로그 — 참고 수준)

### 반복 업무 Top 4
| 순위 | 업무 | Gen UI 적용 아이디어 | 우선순위 |
|---|---|---|---|
| 1 | **상담 준비** — 보장분석, 설명자료 작성 | 고객 선택 시 보장 공백 카드 + 설명자료 초안 조합 | ✅ 1차 범위 |
| 2 | **기존 고객 관리** — 갱신·만기, 문의 대응, 보험금 청구 지원 | 오늘의 브리핑에서 D-day 순 카드 정렬 | ✅ 1차 범위 |
| 3 | **행정·전산** — 청약 서류, 고지사항 정리 | 진행 중 청약 상태 + 누락 서류 체크리스트 | 보류 (전산 연동 없이는 목업이 얕음) |
| 4 | **일정·가망고객 관리** | 일정 타임라인 + 연락 대상 추천(근거 표시) | 보류 (AI 대체 어려운 영역) |

## 4. FC 페르소나와 하루 업무 흐름

### 4-1. 모집단 데이터
- 생보사 설계사 중 50대 이상 58.7% (50대 39.4%, 60대 이상 19.3%, 40대 26.8%, 30대 10.8%, 20대 3.7%) — 이투데이, 2025
- 생보 설계사 평균 연령 51.4세 — 보험연구원 보고서 인용
- 2024년 생보 전속설계사 중 60세 이상이 남성 19.9%, 여성 21.2%로 가장 큰 비중 — 보험연구원 「보험설계사 고령화와 시사점」
- 설계사 시험 응시자 중 50대 비율 10% → 28%, 60세 이상 0.48% → 10% (2010→2024). 신규 고령 설계사의 상품 이해도 부족 → 불완전판매 위험 지적
- 삼성생명 10년차 이상 컨설턴트 34.8% (2022년 7월)
- N잡 설계사 월평균 소득 13만 원 수준 (금감원, 2025년 기준) → **범위 제외**

### 4-2. 페르소나
**① 메인 — 베테랑 FC "정미경" (54세, 경력 15년)**
- 기존 고객 300명 이상, 소개 영업 중심, 관계 관리가 강점
- 디지털 도구는 필요한 것만 사용. 작은 글씨·복잡한 메뉴 기피
- 고민: 고객이 많아 갱신·만기·청구 타이밍을 놓침. 신상품 구조 파악에 시간 소요
- 핵심 시나리오: **② 기존 고객 관리**

**② 서브 — 신입 FC "김현수" (51세, 경력 8개월, 회사원 출신)**
- 은퇴 후 전직. PC는 익숙하나 보험 상품 지식 부족
- 고민: 상담 준비에 시간이 오래 걸리고, 고객 질문에 잘못 답할까 불안
- 핵심 시나리오: **① 상담 준비**

### 4-3. 정미경 FC의 하루 (가설 — 지점 출근·모바일 앱 존재는 확인됨)
| 시간 | 하는 일 | 기기 | 불편한 점 | Gen UI 개입 지점 |
|---|---|---|---|---|
| 08:30–09:30 | 지점 출근, 조회·교육 | PC | 시스템 볼 틈 없음 | 없음 |
| 09:30–10:30 | 오늘 연락할 고객 확인, 전화 | PC + 전화 | 여러 화면을 돌아다니며 확인 | **아침 브리핑** (pc): 갱신·만기·청구·기념일 D-day 순 카드 |
| 10:30–12:00 | 오후 방문 고객 상담 준비 | PC | 보장분석·설명자료 준비 시간 | **상담 준비 화면** (pc): 보장 공백 카드 + 설명 포인트 |
| 13:00–17:00 | 고객 방문 상담 1~3건 | 모바일 앱 | 이동 중 다음 고객 정보 빠르게 확인 | **이동 중 요약** (mo): 고객 1명당 카드 1장 |
| 17:00–19:00 | 상담 결과 기록, 청약·서류 처리 | PC | 행정 부담 | 1차 범위 밖 (전산 연동 필요) |

### 4-4. 설계 반영 원칙
1. **카드는 적게, 글씨는 크게** — 주 사용자 50대 이상. 카드 수 상한을 카탈로그 규칙으로 강제 (pc 5장 / mo 3장).
2. **입력창은 진짜 보조** — 카드 탭이 기본 동작. 음성 입력은 향후 검토 후보.
3. **같은 데이터, 페르소나별 다른 조합** — 같은 고객이라도 베테랑에게는 "오늘 연락할 사람", 신입에게는 "이 상품은 이렇게 설명" 중심으로 조합. **Gen UI를 쓰는 이유를 보여주는 핵심 장면.**

## 5. 회사 제안 대비 체크리스트

### 제안 형태
- **PoC(개념 검증)로 제안** — 전사 도입이 아니라 시나리오 1·2만 다룬 작은 범위.
- **기존 Vue 2 시스템 전면 전환을 전제하지 않음** — 별도 Nuxt 4 앱으로 분리 운영(신규 화면·마이크로 프론트엔드)하는 공존 방식을 함께 제시.
- **기존 FC 모바일 앱과 경쟁하지 않음** — 웹뷰 모듈로 붙는 형태로 제시.
- **"AI 결과를 믿을 수 있나?"에 대한 답을 먼저 준비** — 1-3 검증 체계와 근거 표시 원칙이 이 질문의 답이 됨.

### 제안 전 사내 확인 사항
- [ ] 사내 생성형 AI 사용 정책, 사용 가능한 LLM(외부 API vs 승인된 내부 모델)
- [ ] 망분리·보안 규정상 외부 AI API 호출 가능 여부
- [ ] 개인정보 처리 기준 (고객 데이터가 LLM에 전달될 경우)
- [ ] 개인 시간에 만든 업무 관련 결과물에 대한 사내 규정(지식재산·겸업)
- [ ] 기존 FC 모바일 앱의 웹뷰 탑재 가능 여부
- [ ] 제안 경로 (팀장 보고 → 유관 부서 등)

### 제안서에 넣을 성공 지표 후보
- 상담 준비 시간 단축 (분 단위, before/after)
- 갱신·만기 연락 누락 건수 감소
- 생성 UI 품질 점수 (루브릭 평균, 스키마 통과율 100% 유지)
- FC 만족도 / 재사용 의향
